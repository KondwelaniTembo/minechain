# Decisions log

Technical decisions for MineChain, with the reason for each.

| Date | Decision | Options considered | Reason |
|---|---|---|---|
| 29 Oct 2026 | **Ethereum tooling:** Hardhat 3 | Hardhat 3, Foundry | The developer already knows Hardhat from a previous project, so time goes on the contract rather than on learning new tooling. |
| 29 Oct 2026 | **Flutter state management:** Riverpod | Riverpod, Bloc | Riverpod is easy to test and keeps logic out of widgets. |
| 29 Oct 2026 | **Local encrypted database:** SQLCipher, exact Flutter package to be confirmed before the offline storage work | None recorded | SQLCipher encrypts the local database with AES-256, which protects cached transactions on a lost or stolen device. |
| 29 Oct 2026 | **Backend hosting:** Render with PostgreSQL | None recorded | Render provides real HTTPS, which certificate pinning needs. |
| 29 Oct 2026 | **Ledger permissioning:** public Sepolia testnet, made permissioned through contract access control | None recorded | The project requires role-restricted write access, and contract access control provides it on a public testnet. Anyone can read the ledger, and only the authorised account can write to it. |
| 31 Oct 2026 | **Certificate pinning:** pin the root CA with a backup root, using a Dart `SecurityContext` that trusts only the bundled roots. The exact roots are to be confirmed from the deployed certificate chain | Pin the exact server certificate; pin the root CA with a backup; run our own server with our own certificate | Render renews certificates automatically, so pinning the exact certificate could lock the app out after a renewal, and running our own server adds too much work. Root pinning survives renewals and still blocks interception through a fake CA installed on the device. |
| 1 Nov 2026 | **Certificate pinning (update to the 31 Oct entry):** pin the issuing root CA plus one backup root, not the exact server certificate. The exact roots will be confirmed from the deployed Render chain on Day 6 | Pin the exact server certificate; pin the issuing root CA with one backup root | Render renews certificates automatically, so an exact pin could lock the app out after a renewal. The proposal's description of pinning will be updated to match. |
| 1 Nov 2026 | **Signing and anchoring:** phones sign with P-256 keys in the Android Keystore. The backend verifies each signature and stores the full record. Authorised backend wallets write a compact record and a hash of the signed record to the contract. Contract-level P-256 verification is future work | (a) secp256k1 keys stored in software on the phone so the contract can use `ecrecover`; (b) full records stored on-chain; (c) contract-level P-256 verification | The Android Keystore does not support secp256k1. (a) Rejected: the key would not be hardware-protected, which weakens NFR-02. (b) Rejected: Sepolia is public, so GPS locations and identities would be exposed permanently. (c) Deferred as future work because of complexity and the deadline. The hash still lets anyone detect a changed record. |
| 1 Nov 2026 | **Scope:** FR-16 (Should Have) added for the signed PDF provenance certificate. QR tag parameters cut. Export left out and recorded as future work, so the custody chain ends at purchase. FR-14 and FR-15 stay cut. Deadline is 10 November 2026 | Add the certificate or leave it out; keep or cut QR tag parameters; add a `recordExport` stage to the contract or leave export out | The certificate had no requirement covering it. Export appears in the project objectives, but `recordExport` was rejected for now: no requirement covers it, and it would not fit the 10 November deadline. |
| 1 Nov 2026 | **Contract design:** OpenZeppelin `AccessControl` (5.6.1, pinned) with `DEFAULT_ADMIN_ROLE` for the deployer and `RECORDER_ROLE` for backend wallets. Stages are None, Registered, InTransit and Purchased, with Purchased final. IDs, actor refs and data hashes are `bytes32`. Storage holds only the latest step, and events hold the full history. All three write functions reject a zero id, actor ref, data hash or weight, even though the backend validates too | Single `owner` or role-based access; `string` or `bytes32` fields; store every step or only the latest | Roles fit several backend wallets and keep the admin key off the server. `bytes32` keeps readable personal data off a public chain. Events give a full history at much lower gas cost than storage. |
| 2 Nov 2026 | **Weight unit:** the contract records weight in whole milligrams as a `uint64` (`weightMilligrams`), replacing whole grams | Whole grams; whole milligrams | Small gold lots and gemstones can weigh less than 1 g. In grams they would be rounded, and a lot under 1 g would round to 0 and be rejected by the zero-weight check. Milligrams record them to the milligram, and `uint64` still holds far more than any real lot. The change was made before deployment because a deployed contract cannot be changed. |
| 2 Nov 2026 | **Backend stack:** Express; the `pg` driver with parameterised SQL and a migrations tool; PostgreSQL installed locally for development; Zod for validation; Argon2 for password hashing, with bcrypt as a fallback; Vitest and Supertest for tests | Express or Fastify; `pg` with migrations or Prisma; local PostgreSQL, Docker or a hosted database; Zod or Joi; Argon2 or bcrypt; Vitest or Jest | Writing real SQL is part of what the thesis shows, and parameterised queries prevent SQL injection. Docker is too heavy for a laptop with 12 GB of RAM. A local database means development and tests work offline. Express is the most widely documented Node framework, so problems are quicker to solve under the deadline. Zod uses one schema to describe and check each request body. Argon2 is the current first choice for password hashing in OWASP guidance, and bcrypt is the fallback if the native Argon2 package will not install on Windows or Render. Vitest is fast and needs little setup for modern JavaScript. |
| 2 Nov 2026 | **Sepolia RPC during the deployment:** the contract deployment transaction (block 12047601) was sent through Alchemy. The `grantRole` transaction (block 12047606) and the verification were completed through the public PublicNode Sepolia RPC. Alchemy remains the main RPC provider | Wait for Alchemy to be reachable again; continue through PublicNode | After the deployment transaction, the mobile network lost its connection to Alchemy. PublicNode needs no API key, and the RPC that sends a transaction does not change its result on-chain. Ignition resumed from its journal without redeploying, so only one contract was created. |
| 3 Nov 2026 | **npm peer dependencies:** `backend/.npmrc` sets `legacy-peer-deps=true` | Pass `--legacy-peer-deps` by hand on every install; downgrade vitest; set it in `.npmrc` | npm 10.9.2 crashed while resolving peer dependencies for vitest 5 (`Cannot read properties of null (reading 'edgesOut')`). Setting it in `.npmrc` means a plain `npm install` works locally and on Render. The cost is that npm no longer installs required peer dependencies, so `vite` (required by vitest) is listed directly as a dev dependency and `npm ls` is checked after adding a package. Remove the setting once a newer npm installs cleanly without it. |
| 3 Nov 2026 | **Public health endpoint:** `GET /health` needs no JWT and is the only route without one. It runs `SELECT 1` and returns 200 when the database answers or 503 when it does not, with no error details | Require a JWT on `/health`; return details such as version and database error; return only up or down | Render's health checks and uptime monitors cannot log in. Returning only up or down means the public route tells an attacker nothing about the system, while the full reason is written to the server log. |
| 4 Nov 2026 | **Accepted audit risk in node-pg-migrate 9.0.0:** keep 9.0.0 despite 3 moderate `npm audit` findings: `glob` ([GHSA-3g3m-2fjr-6pw4](https://github.com/advisories/GHSA-3g3m-2fjr-6pw4), AbortSignal cancellation bypass), `minimatch` ([GHSA-g3hv-75wg-m249](https://github.com/advisories/GHSA-g3hv-75wg-m249), denial of service through glob pattern amplification), and `node-pg-migrate` itself, flagged because it depends on that `glob`. Re-check during the Day 10 security review, and upgrade when a node-pg-migrate release moves to a fixed `glob` | (a) Downgrade to node-pg-migrate 7.6.1, the fix `npm audit fix --force` suggests; (b) force newer `glob` and `minimatch` through npm `overrides`; (c) accept the risk | The vulnerable code runs only when migrations run, during deployment and the database test setup, never while the API handles requests. The glob pattern that finds migration files is fixed in the tool and our scripts, and never comes from user input, so the amplification issue cannot be triggered from outside. We pass no abort signal, so the cancellation bypass does not apply. (a) Rejected: a major-version downgrade is a breaking change, and it would move away from the documented v9 behaviour this setup relies on. (b) Rejected: forcing dependency versions node-pg-migrate was not released or tested with could break migrations in ways the audit cannot see. |
| 4 Nov 2026 | **Migrations:** node-pg-migrate 9 with plain SQL files in `backend/migrations/`, one per table | node-pg-migrate; postgres-migrations; graphile-migrate | node-pg-migrate is current and maintained, and works with `pg` 8 and Node 22. It runs pending migrations in one transaction, under a lock, and checks their order. Plain SQL keeps the schema readable as evidence for the thesis. postgres-migrations has had no release since 2022. graphile-migrate's workflow is more to learn before the deadline. |
| 4 Nov 2026 | **Database tests:** a separate `npm run test:db` against `minechain_test`, which migrates the database first and runs each test in a transaction that is rolled back | Run them in `npm test`; delete rows after each test | `npm test` stays fast and works with no database. A rollback cannot forget a table, and the configuration check refuses a test database URL that matches the development one. |
| 4 Nov 2026 | **Account statuses (D1):** `pending`, `active`, `suspended` and `rejected`, with `status_reason` required for suspended and rejected accounts | Three statuses without `rejected`; delete rejected requests | FR-12 rejects requests with a reason. Without `rejected`, a rejected request would have to be deleted or would look the same as a suspended account. *Update 11 Nov 2026: there are now five statuses. `invited` was added for officer and administrator accounts created by an administrator and not yet activated (Accounts (1), migration `1794441600000_users-activation`).* |
| 4 Nov 2026 | **Consignment facts (D2):** weight, GPS origin, capture time and chain hash are stored only on the registration step in `transactions`, not on `consignments` | Store them on both tables, as the original design did | The same fact in two tables can disagree, which 3NF avoids. The signed registration step is the evidence, so it holds the only copy. |
| 4 Nov 2026 | **Held consignments (D3):** a consignment counts as held while any alert on its steps is `open`. This is worked out by a query, not stored | A `held` flag on `consignments` | There is nothing to keep in sync. Closing the last open alert releases the hold automatically. |
| 4 Nov 2026 | **Zone boundaries (D4):** one `jsonb` polygon of `[lat, lng]` corners per zone, checked by a database CHECK and by a point-in-polygon function in the service | A table of vertices; PostGIS | The polygon is always read whole, so a vertex table adds joins for no benefit. PostGIS would be cleaner, but it is another install on Windows and on Render. |
| 4 Nov 2026 | **Signer key per step (D5):** each transaction stores a copy of the public key that signed it, as well as `users.public_key` | Only `users.public_key` | A lost phone means a new key pair. With only the user's current key, every earlier signature would stop verifying. The stored key is a historical fact, like the price on an invoice, not duplication. |
| 4 Nov 2026 | **Anchoring states (D6):** `pending`, `submitted`, `confirmed` and `failed` | `pending`, `confirmed` and `failed` | `submitted` covers the time between sending to Sepolia and the transaction being mined. If the server stops at that moment, the worker checks the stored `chain_tx_hash` on-chain before resending. Without it, a crash could repeat a non-idempotent `recordHandoff`. |
| 4 Nov 2026 | **Tamper alerts (D7):** a sixth alert type, `record_tampered`, beside the five anomaly checks | Five alert types only | A database record that no longer matches its anchored hash must raise an alert (contract specification, section 7). It is found by verification, not during sync, so the five checks are unchanged. |
| 4 Nov 2026 | **Audit log IDs (D8):** `audit_logs.id` is a `bigint` identity, not a UUID | UUID | It shows insert order at a glance and is smaller. Log entries are never created offline, so UUIDs bring no benefit. |
| 4 Nov 2026 | **Deleting accounts (D9):** foreign keys use `ON DELETE RESTRICT`. Only a user with no history can be hard-deleted; anyone else is suspended | Allow deletion, with `CASCADE` or `SET NULL` | FR-10 mentions deleting accounts, but deleting a user who has consignments, steps, reviews or log entries would break the audit trail. |
| 4 Nov 2026 | **Push device tokens (D10):** a small seventh table for FCM tokens will be added with the push notification work | Add it now | It is not needed until push notifications (FR-08) are built. |
| 4 Nov 2026 | **Append-only audit log:** two statement-level `BEFORE` triggers refuse `UPDATE`, `DELETE` and `TRUNCATE` on `audit_logs` | Row-level triggers; permissions only | A statement-level trigger refuses the statement even when no rows match, while a row-level trigger would let a non-matching `UPDATE` succeed. `TRUNCATE` supports only statement-level triggers. Permissions alone are not possible yet, because one database user owns the tables. The table owner can still disable the triggers. This is recorded as a limit, with separate roles and hash-chaining as future work. |
| 4 Nov 2026 | **Zone boundary check (fix):** the corner check uses `strict` jsonpath inside a `CASE` that first confirms the boundary is an array | The default lax jsonpath; `silent => true` | In lax mode the filter unwraps each `[lat, lng]` corner into two numbers, so every boundary failed, including valid ones. The tests caught this because valid boundaries were also tested. Strict mode raises an error on a non-array, so the `CASE` makes that a normal CHECK failure. `silent => true` was rejected because a hidden error returns NULL, which a CHECK lets through. |
| 4 Nov 2026 | **`consignments.stage` (exception to 3NF):** the current stage is stored on `consignments`, although it could be worked out from the latest accepted step | Work it out from `transactions` on every read | The stage is read on almost every request, for the stage-order check and for every consignment list. The service updates it in the same database transaction as the step, while holding the consignment row with `SELECT … FOR UPDATE`, so the two cannot disagree. It mirrors the contract's own stored stage. |
| 4 Nov 2026 | **Coordinate precision:** latitude and longitude have at most 6 decimal places. The app rounds to 6 places before signing, and the API rejects more instead of storing a rounded value | Let `numeric(9,6)` round | PostgreSQL silently rounds extra decimal places, so the stored point would differ from the signed record and verification against the columns would fail. Six places is about 11 cm, finer than phone GPS. |
| 4 Nov 2026 | **Password hashing settings:** Argon2id with 19 MiB of memory (`memoryCost` 19456 KiB), 2 passes, 1 thread, a fresh 16-byte salt and a 32-byte output, using the `argon2` package 0.45. Passwords are normalised to Unicode NFKC before hashing and before checking. At each successful login, `needsRehash` spots a hash made with older settings and replaces it | The library default (64 MiB, 3 passes, 4 threads); bcrypt, the approved fallback, which is not installed | These are the OWASP Password Storage Cheat Sheet minimum for Argon2id. Render's free instance has 512 MB of RAM: ten logins at once need about 190 MB at 19 MiB, but 640 MB at 64 MiB. One check takes about 50 ms. The settings are stored inside every hash, so they can be raised later and existing users are upgraded at their next login. NFKC makes the same-looking text typed on different keyboards give the same hash. |
| 4 Nov 2026 | **Password policy (deviation from NIST):** 12 to 128 characters after NFKC normalisation, spaces allowed, no composition rules. A password is refused if it is one character repeated, contains the username, or is on a list of 1,186 common passwords. The list is taken from SecLists' NCSC 100k list (MIT licence, filtered to 12 or more characters), with its licence beside it. The policy applies at registration only, never at login | 8 characters, the OWASP ASVS 5.0 minimum; 15 characters, which NIST SP 800-63B rev. 4 requires when the password is the only factor and ASVS recommends | 12 is a deliberate deviation from NIST's 15. NFR-06 asks for plain, easy use by miners with limited English, and a three-word passphrase such as "gold river kasempa" meets 12. The blocklist and Argon2's cost make up part of the gap. Composition rules are left out, as NIST advises, because they make passwords harder to remember without making them much harder to guess. Not applying the policy at login means a password accepted under an older rule never locks its owner out. |
| 4 Nov 2026 | **Session tokens:** JWTs signed with HS256 only, using `jose` 6. The claims are `sub` (user id), `role`, `iat`, `exp`, `iss` (`minechain-api`) and `aud` (`minechain-app`), with no personal data. The lifetime comes from `JWT_EXPIRES_IN` and is capped at 60 minutes, both in the config and in the token service. `JWT_SECRET` must be at least 43 characters. Verification allows only HS256 and reports only `TOKEN_EXPIRED` or a generic `TOKEN_INVALID`. Login responses carry `Cache-Control: no-store`. There are no refresh tokens | `jsonwebtoken` 9; ES256 with a key pair; refresh tokens | One service both issues and checks tokens, so a shared secret is enough. ES256 would only matter if other services had to check tokens without being able to issue them. Allowing only HS256 refuses `alg: none` and algorithm-confusion forgeries. 43 base64url characters carry the 256 bits HS256 needs. `jose` has no dependencies and requires the algorithm list. The 60-minute cap meets NFR-01. Offline work is signed on the phone and needs no token, so after expiry the user simply logs in again on reconnect. |
| 4 Nov 2026 | **Rate limits:** registration 30 per IP per hour; login 100 per IP per 15 minutes; login 10 failed attempts per username per 15 minutes, where successful logins are not counted. Over the limit, the API answers 429 `TOO_MANY_REQUESTS` in the normal error format, with RateLimit headers and `Retry-After`. Each limiter is created inside `createApp`, so every app instance has its own counters | The tighter per-IP limits first planned (login 20 per 15 minutes, registration 10 per hour); no limits until the security review | Zambian mobile networks use carrier-grade NAT, so many phones, sometimes a whole mining site, share one public IP. Tight per-IP limits would block everyone on that network because of one person. The per-username limit is what stops password guessing against one account; the per-IP limits only slow one source trying many usernames. |
| 4 Nov 2026 | **`TRUST_PROXY` is a hop count:** a whole number from 0 to 5, default 0 (Render is planned to need 1). `createApp` calls `app.set('trust proxy', hops)` only when it is above 0 | `trust proxy` set to `true`; always calling `app.set`, even with 0 | With a hop count, Express takes the client address added by our own proxy and ignores any addresses a client forged further left in `X-Forwarded-For`. With `true`, a client could invent a new address for every request, escaping the rate limits and putting false addresses in the audit log. Leaving Express's default (`false`) when there is no proxy keeps express-rate-limit's `ERR_ERL_UNEXPECTED_X_FORWARDED_FOR` warning active, which would point out a wrong `TRUST_PROXY` in production. |
| 5 Nov 2026 | **Login username limiter key:** the key is an HMAC-SHA256 of the trimmed, lower-cased username, made with a random 32-byte key generated per process | Using the plain username as the key | The rate-limit store keeps its keys in memory. Plain usernames there would be a list of everything typed into the username box, including passwords typed there by mistake. An HMAC gives the same counter for the same username but cannot be turned back into it. Trimming and lower-casing make `Mutale_Banda` and ` mutale_banda ` share one counter, as they share one account. |
| 5 Nov 2026 | **Self-registration roles (FR-12):** `POST /auth/register` accepts only `miner`, `transporter` and `buyer`. Officer and administrator accounts are created by an administrator (FR-10). New accounts are always `pending`: the status is written in the SQL, and the request schema refuses any field it does not list | Also allowing `officer` | FR-12 names miners, transporters and buyers. Officers can see every record and review every alert, so nobody should be able to request that access through a public endpoint, even if an administrator would still have to approve it. |
| 5 Nov 2026 | **Authenticated requests check the database every time:** `requireAuth` reads only the `Authorization: Bearer` header (never the query string), checks the token, then loads the user by id. `req.user` is the user as the database has it now. A user who no longer exists, or whose role differs from the token's, gets 401 `TOKEN_INVALID`. A pending, suspended or rejected account gets 403 with its own code (`ACCOUNT_PENDING`, `ACCOUNT_SUSPENDED`, `ACCOUNT_REJECTED`), the same codes as at login. These replace the single `ACCOUNT_NOT_ACTIVE` first planned, which remains only as a fallback for a status added later. Every 401 from `requireAuth` carries a `WWW-Authenticate: Bearer` header | Trusting the token's claims until it expires; one shared 403 code | A suspension or role change then takes effect on the next request instead of up to 60 minutes later, for the cost of one primary-key lookup. The rule: 401 when logging in again could fix it, 403 when the account itself is not allowed in. URLs are written to access and proxy logs, so a token must never travel in one. |
| 5 Nov 2026 | **Failed-login audit entries are written outside any transaction:** `user.login_failed` (with a reason only: `unknown_username`, `wrong_password` or `account_<status>`) is written with the top-level database connection, then the error is thrown. Only a successful login opens a transaction, for the optional rehash and the `user.login` entry. The typed username and password are never stored | Writing the entry inside a transaction | Authentication throws straight after recording a failure, and a throw inside a transaction would roll the entry back, erasing exactly the evidence an officer needs when someone is guessing passwords. People sometimes type their password into the username box, so the typed username is never recorded either. |
| 5 Nov 2026 | **Refused tokens are not audited (for now):** no audit entry is written for a missing, malformed, expired, forged or refused token. For the Day 10 security review: consider a throttled `user.token_refused` entry, for example at most one per user per token, written only when a genuine token is refused for an account reason (suspended, rejected, role changed) | Auditing every refused token | Expired tokens are routine, and garbage tokens are entirely attacker-controlled. Without a throttle, anyone could fill the append-only `audit_logs` table with rows that can never be removed. A genuine token refused because the account was suspended is a real security event, but the app retries on its own, so it needs a throttle before it is recorded. Meanwhile the exposure is bounded: every such request is already refused, and the token expires within 60 minutes. |
| 5 Nov 2026 | **Known limitation, in-memory rate-limit stores:** all three limiters keep their counts in the server's memory, marked `DEV-SHORTCUT` in `backend/src/middleware/rateLimits.js`. The counts reset when the server restarts, each server instance counts separately, and the username limiter's HMAC key changes at each restart | A shared store (PostgreSQL or Redis) now | The prototype runs as one instance. Before running more than one instance, the stores must move to a shared store, and the username limiter must get a configured HMAC key. |
| 5 Nov 2026 | **Known limitation, username lockout:** someone who knows or guesses a username can use up its 10 failed attempts and block its owner from logging in for up to 15 minutes. The block applies the same way to usernames that do not exist, so it does not reveal which accounts are real | A combined IP-and-username key; CAPTCHA; growing delays instead of a block | This trade-off was accepted for the prototype: without the per-username limit, passwords could be guessed from many IP addresses. The lockout is limited to 15 minutes, and the owner's successful logins do not count towards it. Alternatives to review on Day 10. |
| 5 Nov 2026 | **Known limitation, usernames visible at registration:** `POST /auth/register` answers 409 `USERNAME_TAKEN` when a username exists, so it reveals which usernames are taken | A generic answer with confirmation by email or SMS | People choose their own usernames and there is no email or SMS channel, so they must be told when a name is taken. Login still reveals nothing: an unknown username and a wrong password get the same answer and take about the same time. |
| 5 Nov 2026 | **Known limitation, two tests not written:** (a) two registrations with the same username arriving at the same moment; (b) a failed-login entry still present after a real commit, seen from a separate connection | Committing test rows to `minechain_test` and removing them afterwards | Both would need real commits. | 5 Nov 2026 | **Known limitation, error logging:** `errorHandler` logs unexpected errors in full, and a PostgreSQL error's `detail` can contain values (for example "Key (…)=(…) already exists"). | 5 Nov 2026 | **Role-based access (`requireRole`):** routes list their allowed roles with `requireRole(...roles)` after `requireAuth`. It reads only `req.user.role`, which `requireAuth` loads from the database on every request, never the token's claim. A role outside the list gets 403 `FORBIDDEN` with a generic message that does not name the allowed roles. The planned access per role is in `docs/api.md` (Roles and access), and keeps administrators out of custody steps and alert review | Reading the role from the token; a 403 when `requireAuth` is missing; checking role names only at request time; auditing every refusal | The database role means a role change applies at once. Checking role names at start-up turns a typo such as `officr` into an immediate failure instead of a route that silently refuses everyone. Naming the allowed roles would tell a caller which account to go after. Refusals are not audited for the same reason as refused tokens: they can be repeated endlessly and would flood the append-only log. They can be considered with the throttled `user.token_refused` idea at the Day 10 review. |

| 6 Nov 2026 | **Seed script (`npm run seed`):** creates the first admin from `SEED_ADMIN_USERNAME` and `SEED_ADMIN_PASSWORD`, the demo zone "ZCAS Campus (demo)", and, outside production and only when `SEED_DEMO_PASSWORD` is set, one active demo user per role (`seed_miner`, `seed_transporter`, `seed_buyer`, `seed_officer`). | 6 Nov 2026 | **Audit actor for seeded rows:** `actor_id` NULL and `ip_address` NULL, with the actions `user.create` and `gps_zone.create` and `details` `{ "source": "seed", … }`.

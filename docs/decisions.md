# Decisions log

Technical decisions for MineChain, with the reason for each.

| Date | Decision | Options considered | Reason |
|---|---|---|---|
| 29 Oct 2026 | **Ethereum tooling:** Hardhat 3 | Hardhat 3, Foundry | The developer already knows Hardhat from a previous project, so time goes on the contract rather than on learning new tooling. |
| 29 Oct 2026 | **Flutter state management:** Riverpod | Riverpod, Bloc | Riverpod is easy to test and keeps logic out of widgets. |
| 29 Oct 2026 | **Local encrypted database:** SQLCipher, exact Flutter package to be confirmed before the offline storage work | None recorded | SQLCipher encrypts the local database with AES-256, which protects cached transactions on a lost or stolen device. |
| 29 Oct 2026 | **Backend hosting:** Render with PostgreSQL | None recorded | Render provides real HTTPS, which certificate pinning needs. |
| 29 Oct 2026 | **Ledger permissioning:** public Sepolia testnet, made permissioned through contract access control | None recorded | The project requires role-restricted write access, and contract access control provides it on a public testnet. Anyone can read the ledger, and only the authorised account can write to it. |
| 31 Oct 2026 | **Certificate pinning:** pin the root CA with a backup root, using a Dart `SecurityContext` that trusts only the bundled roots. The exact roots are to be confirmed from the deployed certificate chain | Pin the exact server certificate; pin the root CA with a backup; run our own server with our own certificate | Render renews certificates automatically, so pinning the exact certificate could lock the app out after a renewal, and running our own server adds too much work. Root pinning survives renewals and still blocks interception through a fake CA installed on the device. |
| 1 Nov 2026 | **Certificate pinning (update to the 31 Oct entry):** pin the issuing root CA plus one backup root, not the exact server certificate. The exact roots will be confirmed from the deployed Render chain on Day 6 | Pin the exact server certificate; pin the issuing root CA with one backup root | Render renews certificates automatically, so an exact pin could lock the app out after a renewal. The proposal's description of pinning will be updated to match. |
| 1 Nov 2026 | **Signing and anchoring:** phones sign with P-256 keys in the Android Keystore. The backend verifies each signature and stores the full record. Authorised backend wallets write a compact record and a hash of the signed record to the contract. Contract-level P-256 verification is future work | (a) secp256k1 keys stored in software on the phone so the contract can use `ecrecover`; (b) full records stored on-chain; (c) contract-level P-256 verification | The Android Keystore does not support secp256k1. (a) Rejected: the key would not be hardware-protected, which weakens NFR-02. (b) Rejected: Sepolia is public, so GPS locations and identities would be exposed permanently. (c) Deferred as future work because of complexity and the deadline. The hash still lets anyone detect a changed record. |
| 1 Nov 2026 | **Scope:** FR-16 (Should Have) added for the signed PDF provenance certificate. QR tag parameters cut. Export left out and recorded as future work, so the custody chain ends at purchase. FR-14 and FR-15 stay cut. Deadline is 10 November 2026 | Add the certificate or leave it out; keep or cut QR tag parameters; add a `recordExport` stage to the contract or leave export out | The certificate had no requirement covering it. Export appears in the project objectives, but `recordExport` was rejected for now: no requirement covers it, and it would not fit the 10 November deadline. |
